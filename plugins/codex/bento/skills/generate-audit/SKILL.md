# Generate Audit

## Compatibility Notice

Use `bento:audit` for direct project audits. `generate-audit` remains only as
a compatibility path for users who explicitly ask to generate a repo-specific
audit plan or a repo-local audit skill.

Do not route ordinary "audit this project" requests here. For those, invoke
the reusable `bento:audit` skill, run discovery, inspect applicable risk
surfaces, and produce the audit report directly.

Name any generated repo-local skill something repo-specific, such as
`project-audit`. Do not name it `audit`: a local skill by that name shadows
`bento:audit` in the same runtime and makes "run the audit skill" ambiguous.

## Legacy Model Guidance

Recommended model: high - legacy generation still requires broad repo
inference and tailored output shaping.

This compatibility entrypoint may produce one of these legacy outputs:

- **audit plan** - a markdown checklist or procedure for a one-off audit
- **draft skill** - a repo-local audit skill (e.g. `project-audit`) ready for
  refinement
- **both** - first the audit plan, then a draft skill from the same findings

## Deterministic Helper

This entrypoint owns no assets of its own. The helper and reference docs live
with the `audit` skill; `../audit/scripts/audit-discover.py` collects the
deterministic base layer of repo facts before shaping any legacy output.

```bash
../audit/scripts/audit-discover.py
```

Use the JSON output as the starting point, then fill gaps using
`../audit/references/discovery-checklist.md`.

## Legacy Workflow

1. Confirm the user explicitly wants generated audit material rather than a
   direct report from `audit`.
2. Run the helper; use its JSON as the deterministic base layer.
3. Work through `../audit/references/discovery-checklist.md` to fill in
   project shape, docs review, interfaces, workflow surfaces, test health,
   risk areas, documentation truthfulness, static analysis, and quality
   standards. Skip surfaces that do not apply.
4. Select only modules that fit the discovered repo, using the "Audit
   Modules" list in `../audit/SKILL.md`. Secrets scan is never optional.
5. Generate the requested legacy output, following
   `../audit/references/generation-rules.md` (see its "Optional Legacy Draft
   Skill Structure" section).
6. When a repo-local audit skill was generated, commit it and record its
   rationale (see "Committing the Generated Skill").

## Guardrails

- Prefer `bento:audit` unless the user explicitly requested generated audit
  material.
- Generate from discovered facts, not assumptions.
- Keep generated output lean and maintainable.
- Do not require issue creation, commits, or memory edits by default.
- Do not execute destructive or environment-mutating commands just because
  they appear in docs.

## Committing the Generated Skill

A generated repo-local audit skill is a tracked project artifact, not scratch
output. After generating it, commit it through the repo's normal issue-backed
flow (branch + worktree, tracker issue, land the change). Do not leave it
untracked or committed with no record of where it came from.

Record a one-line rationale in the repo's agent doc (`AGENTS.md`, `CLAUDE.md`,
or equivalent) so a future maintainer knows what produced the skill and when to
refresh it. Use this template:

```markdown
`.claude/skills/project-audit/` is generated by `bento:generate-audit`;
regenerate when the repo's stack, build/test commands, or risk surfaces change
materially.
```

Adjust the path and trigger to match the actual output location and the repo's
real drift sources. This closing step applies to the generated skill only; a
one-off audit plan needs no commit or rationale line.

For the current direct audit workflow, use `../audit/SKILL.md`.
