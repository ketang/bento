# Host-wide admission governor contract

**Date:** 2026-09-23

**Status:** Design complete; implementation pending in `bento-dyp7.2`

**Contract version:** 1 (`bento-governor-v1`)
**Owner:** Bento (`bento-dyp7.1`)

## Scope and invariants

One governor installation arbitrates heavy jobs from Bento, Shatter, PickPackIt, and Kapow on this host. All participating users and repositories share one capacity pool. Every admitted job runs in a transient systemd scope with a memory limit; its lease lasts until that scope's cgroup is empty, including after the invoking client is killed. A job never starts on a timeout, unreadable signal, unavailable scope, unavailable state store, or failed audit write. The only exception is an explicit, authenticated, logged operator bypass described below. This contract does not govern processes that do not call the CLI, and does not cap agent sessions, language servers, or daemons outside a job scope.

The governor is Linux/cgroup-v2/systemd-specific. On an unsupported host it returns an infrastructure error. It does not silently fall back to the old `run-heavy` behavior. The mixed-project stress exercise remains separately approved work; deterministic integration tests are sufficient for `bento-dyp7.2`.

## Implementation and installation

Implement a Python 3.12 standard-library client and host service under `governor/` in Bento, with `governor/bin/bento-governor-v1` as the source entrypoint and a systemd service unit under `governor/systemd/`. The service owns admission, scope creation/monitoring, and a SQLite database. A system service and a Unix socket at `/run/bento-governor/v1.sock` are intentional: a per-repository semaphore or per-user runtime directory would split the host-wide pool. Authenticate local clients with Unix peer credentials; allow only configured caller UIDs/groups. Run commands as the requesting UID in a scope owned by the system manager. The service must not take arbitrary shell strings: it receives an argv vector, current directory, and explicitly forwarded environment and file descriptors.

Install a *pinned* version from a reviewed Bento commit to `/opt/bento-governor/v1/<release>/` and expose `/usr/local/bin/bento-governor-v1`. `--version` prints the contract version, implementation version, and source commit. Installation changes the pinned target only as a deliberate deployment; a Bento plugin-cache refresh never changes it. Adapters call `/usr/local/bin/bento-governor-v1` and require contract major 1. The service rejects a client with an incompatible protocol major. Packaging and the host installation procedure belong to `bento-dyp7.2`; no adapter uses a transient `~/.codex/plugins/cache/...` path.

The host service's administrator-owned `/etc/bento-governor/v1.toml` sets capacity, allowed callers/operators, polling interval, and thresholds. It is not writable by a caller. The service and CLI use a versioned wire protocol. A restart reconciles durable leases against their systemd units before accepting another request; an unknown or unverifiable unit retains its reserved weight and blocks admission until an operator repairs it. Waiting requests are connection-owned and do not survive a service restart; disconnected clients receive 70 and must explicitly retry. The service has no timeout that frees an unverified lease.

## Client CLI and results

```text
/usr/local/bin/bento-governor-v1 run [--weight N | --exclusive] [--max-wait SECONDS] [--result-file PATH] --repo REPO --label LABEL -- CMD [ARG...]
/usr/local/bin/bento-governor-v1 signals --json [--weight N | --exclusive] [--cwd PATH]
/usr/local/bin/bento-governor-v1 events --jsonl [--since RFC3339]
/usr/local/bin/bento-governor-v1 --version
```

`--` is mandatory. `REPO` is a stable repository name (for example `shatter`), and `LABEL` is a stable gate/target name. The caller supplies both explicitly; the service also records its authenticated UID and actual working directory. `--weight` is a positive decimal integer, default 1. `--exclusive` requests all capacity. Effective weight is `min(requested_weight, capacity)`; both the request and the clamp are logged. `--max-wait` defaults to unlimited. Zero means a single immediate attempt. Positive values use a monotonic deadline; expiration **returns without launching the command**. The service checks signals again in the same serialized admission decision that reserves weight. Requests queue in arrival order; an exclusive request waits for all other leases, and a large request is not perpetually overtaken by small requests. The queue is in memory, owned by live client connections. A disconnect cancels an ungranted request, and the service must never launch its command later. A service restart fails all queued requests closed; clients reconnect by issuing a new request.

The CLI passes the child's exit status through, including nonzero values. It emits one human-readable final diagnostic on stderr, prefixed `BENTO_GOVERNOR_RESULT ` and followed by one compact JSON object with `schema_version: 1`, `outcome`, `lease_id` (null before acquisition), `wait_seconds`, and `child_exit_code` (null if never started). A child can print the same prefix, so **machine consumers must use `--result-file`**, which atomically writes that JSON, mode 0600; they distinguish the origin using `outcome`, never the numeric status alone. The client creates and verifies the result-file destination before asking for admission. A final result-file write failure after launch is logged and reported as an infrastructure error without pretending that the job never ran.

| Case | Exit status | `outcome` | Child started? |
| --- | ---: | --- | --- |
| Invalid CLI or caller-supplied option | 64 | `invalid-args` | No |
| Immediate pressure/capacity denial (`--max-wait 0`) or policy denial | 69 | `denied` | No |
| State, audit, scope, or required-signal error | 70 | `infra-error` | No, except a detected post-launch error |
| Wait deadline elapsed | 75 | `timeout` | No |
| Child completed normally | Child status, including 0 | `completed` or `child-failed` | Yes |
| Scope had any OOM kill | 137 | `oom-killed` | Yes |

SIGINT/SIGTERM sent to the client is forwarded to the scope; the client waits for the scope to empty and returns the conventional signal status if no OOM occurred. A SIGKILLed client cannot forward a signal, but the service keeps the lease until the cgroup empties and records a `client-lost` event, then a final release with the child's status if recoverable (otherwise null). There is no client exit result after the client itself is killed. If OOM and a client signal both occur, `oom-killed` takes precedence in the final event and any surviving client's result. Adapters may read `wait_seconds` from the result to populate existing queue-timing fields; the event stream is the durable source if the client was killed.

## Capacity and nested calls

The initial host default is `capacity = min(floor(online_cpus / 4), floor((MemTotal - 8 GiB) / 4 GiB))`, with a minimum of 1 only when `MemTotal >= 12 GiB`. This yields 8 on the currently observed 32-CPU/48-GiB host. Smaller hosts without the minimum headroom fail configuration validation and require an explicit reviewed capacity. A weight unit reserves a 4-GiB hard memory budget, so the sum of admitted budgets is at most `capacity × 4 GiB`; the default formula leaves at least 8 GiB outside governed budgets. This is an initial conservative policy, not a claim that a weight-1 build has been empirically sized. `bento-dyp7.2` must expose each scope's peak memory in release events so adapters can tune requested weights using measurements. The administrator may change capacity or unit budget only with a documented host configuration change; callers cannot raise their own memory limit independently of weight.

The service creates a scope with `MemoryMax=effective_weight × 4 GiB`, `MemorySwapMax=0`, and `OOMPolicy=kill` (or an equivalent whole-scope kill mechanism). It verifies the configured limits before executing the command. Continue the old `nice -n 10` and `ionice -c 3` behavior for governed jobs. CPUWeight/IOWeight may be added after measurement; they do not replace the existing priority behavior in v1.

The service issues an unpredictable lease token to the command. A nested `run` presents that token and is re-entrant only when the peer process is verified to be inside the token's live scope cgroup. A copied or stale environment token alone is insufficient. A nested request with effective weight no greater than its outer reservation runs within that same scope, inherits the outer deadline and memory limit, and makes no second capacity reservation. A nested request that demands more weight or `--exclusive` when the outer lease is smaller is denied with 69; callers must size the outer lease for the full DAG. The nested call produces its own event with the parent lease ID but cannot release the parent lease.

The lease registry lives in `/var/lib/bento-governor/v1/state.sqlite3`, owned by the service; the wait queue is in memory. SQLite transactions serialize capacity and event decisions; `journal_mode=WAL` and `synchronous=FULL` are required. No per-slot `flock` held by the invoking wrapper is used: a wrapper can die while children continue, and dropping its file descriptors would release too early. The launch sequence is: (1) reserve weight and commit an acquire event; (2) fork a minimal executor under the caller UID that blocks on a daemon-owned pipe **before** it can exec the requested command; (3) attach that PID to a transient systemd scope through `StartTransientUnit` with the memory properties, then verify the unit, cgroup membership, and effective limits; (4) commit the unit/cgroup identity to the lease row; (5) release the executor's pipe so it may exec. The executor must not fork the command before step 5. The service acknowledges acquisition to the client only after step 4. If any stage fails, kill the blocked executor and scope, verify the cgroup is empty, durably record release, and return 70 without running the command. If emptiness cannot be proven, keep the reservation and fail closed. A release commits only after the scope's `cgroup.events populated` becomes 0 (or equivalent verified systemd empty state), and after OOM outcome collection. Service restart reconciles every reserved scope before reopening admission. A reservation with no persisted scope identity may be released only after the service proves that its executor PID is gone and no unit with the lease's deterministic name exists; otherwise it remains reserved for operator repair. This ordering is an implementation requirement; calling `systemd-run --scope CMD` directly is insufficient because CMD could run before limits and audit are verified.

## Pressure contract

Admission requires **all** signals below to be ready. A threshold breach waits (or denies immediately for `--max-wait 0`); missing, unreadable, malformed, unsupported, or invalid configuration fails closed with 70. Recheck every 10 seconds by default and on a lease release; do not run after a maximum wait. The service samples and reserves under one admission decision, while recognizing that host pressure can change after launch. The defaults intentionally reuse Shatter's current `gate-pressure.py` thresholds and reason names, except that the governor treats unsupported PSI as an error. Shatter's local pre-check may remain advisory, but its ready verdict never replaces a governor acquisition.

| Signal | Source | Ready when | Default | Override key |
| --- | --- | --- | ---: | --- |
| `mem_available_bytes` | `/proc/meminfo` `MemAvailable` | `>= max(8 GiB, requested_budget + 4 GiB)` | 8 GiB floor | `min_mem_bytes` |
| `memory_full_avg10` | `/proc/pressure/memory` `full avg10` | `<=` | 1.0% | `max_memory_full_avg10` |
| `io_some_avg10` | `/proc/pressure/io` `some avg10` | `<=` | 20.0% | `max_io_some_avg10` |
| `cpu_some_avg10` | `/proc/pressure/cpu` `some avg10` | `<=` | 20.0% | `max_cpu_some_avg10` |
| `disk_free_bytes` | `statvfs` available bytes | `>=` for every distinct filesystem | 10 GiB | `min_disk_bytes` |
| `load1` | `/proc/loadavg`, scaled by online CPUs | `<=` | `1.5 × online_cpus` | `max_load_factor` |

Disk paths are the actual working directory, build target, temp directory, cache directory, SQLite/log filesystem, and any administrator-configured extra path. For a not-yet-created directory use its nearest existing ancestor; deduplicate by device as Shatter does, but retain all checked paths in diagnostics. A missing required path is an error. Disk thresholds are checked on each distinct filesystem, not just the minimum across arbitrary paths. The `load1` check preserves the previous load-wait behavior from `run-heavy`; CPU PSI is independently **blocking**, including a CPU-only overload from another repository.

`signals --json` samples a hypothetical request with its supplied weight (default 1) and filesystem paths resolved from `--cwd` (default the caller's actual cwd) and the same target/cache/temp environment used by `run`. It does not reserve capacity, so its verdict is diagnostic and may change before a later `run`. It returns schema v1: `{ "schema_version": 1, "status": "ready|blocked|error", "signals": [...] }`. Each signal has `name`, `status`, `value`, `threshold`, `comparison` (`min` or `max`), and `reason`. Threshold breaches use `below_min`/`above_max`; unavailable sources use `unsupported`, `missing`, `unreadable`, or `malformed`; a bad administrator override uses `invalid_override`. Each error also has `detail`. Numeric values are finite and use bytes or percentages as named. `signals` exits 0 for a successfully sampled ready or blocked state, 70 for error. This copies Shatter's JSON v1 shape and vocabulary, but its default handling of absent PSI (`unsupported` without blocking) is deliberately tightened. The service and Shatter may share a parser/test fixture; the governor never reads `SHATTER_GATE_*` environment variables. Thresholds come only from the administrator file, preventing a job from silently relaxing admission.

## Scope lifecycle, OOM, and external daemons

The service monitors the scope cgroup's `cgroup.events` and `memory.events` while the scope exists. Any increase in `oom_kill` is an `oom-killed` result even if a shell wrapper exits 0. The service stops/kills the whole scope on detection, waits until it is empty, then releases its weight. It must keep an open cgroup handle or another reliable systemd OOM result so a quickly disappearing cgroup cannot erase the evidence; an unreadable/ambiguous OOM result is an infrastructure error, not a successful run. The scope's `memory.peak` becomes `peak_memory_bytes` in the release event. This is a containment mitigation: the memory limit bounds governed descendants, but ungoverned host processes can still grow and exhaust memory.

Long-lived daemons do not become descendants merely because a scoped job contacts them. The host installation must document and separately cap sccache's server scope; Docker adapters must pass a container `--memory` limit compatible with the lease budget and count daemon-side work in their resource plan. These processes are outside the job scope; the governor must not claim their memory is contained by it. Until those caps are configured, the relevant adapter is not ready to claim memory containment. In-process compilation solely to force scope membership is not the default because it loses sccache reuse.

## Durable events and operator bypass

The same SQLite database contains an append-only `events` table committed with lease state changes. `events --jsonl` emits one schema-v1 object per record in sequence order; auditing does not require raw database access. The service records `acquire`, `deny`, `timeout`, `infra-error`, `client-lost`, `oom-killed`, `release`, and `bypass` events. Each has `schema_version`, monotonically increasing `event_id`, RFC3339 UTC `timestamp`, `lease_id`, `parent_lease_id`, authenticated `uid`, `repo`, `label`, `requested_weight`, `effective_weight`, `wait_seconds`, `outcome`, `reason`, and, where applicable, `scope_unit`, `peak_memory_bytes`, signal snapshot, and child exit code. A bypass also records `operator_uid`, `operator_tty`, and the exact nonempty operator reason. Release has the same identity and weight fields as acquire. Record an acquire and bypass durably **before** starting a command; an audit transaction failure is an infrastructure error and never authorizes execution. If the store itself fails, the error is reported on stderr and no durable error event can be promised. If a release write fails, keep the lease reserved until recovery can durably record the release.

An allowlisted human operator may run:

```text
bento-governor-v1 run --bypass=admission --reason 'ticket and emergency reason' --weight N --repo REPO --label LABEL -- CMD...
bento-governor-v1 run --bypass=uncontained --reason 'ticket and emergency reason' --repo REPO --label LABEL -- CMD...
```

The service verifies the peer UID is in its operator allowlist, the client has a real controlling TTY, and an interactive polkit challenge for the `org.bento.governor.bypass` action succeeds for that peer process. Installing the policy and an authentication agent is part of deployment; if unavailable, bypass is denied. This verifies an authenticated operator action rather than trusting a UID and inherited PTY alone. Neither an environment variable nor a project config can grant bypass. `admission` skips capacity and pressure checks but still requires a working state/audit store and a verified memory-limited scope; it records the requested weight and still counts that scope as an over-capacity lease for future decisions. `uncontained` is the explicit last resort when a systemd scope cannot be created: it requires the state/audit store, logs `bypass` with `outcome: uncontained` before starting, and logs completion when observed. It has no containment or crash-safe release guarantee and is never selected automatically. If the audit store or authentication is unavailable, **both bypass forms fail closed**. A bypass does not silently change the normal CLI's result or event schema.

## Verification and migration obligations

`bento-dyp7.2` must add deterministic tests with fake clock, pressure provider, scope/cgroup provider, and state-store fault injection for weighted concurrency, clamp/exclusive, FIFO behavior, CPU-only and load-only blocking, missing PSI, disk/memory/I/O blocking, timeout without spawn, SQLite/log error before spawn, crash/restart reconciliation, nested cgroup verification, scope-empty release after normal exit/TERM/client SIGKILL, OOM child killed while wrapper exits 0, and both audited bypass modes. A real-entrypoint smoke on the configured host must verify `bento-governor-v1 run --repo bento --label smoke -- echo ok`, `signals --json`, event visibility, and an actual transient scope with its memory limit. The old `run-heavy` verification is replaced one-for-one: idle `echo ok`, a controlled high-load wait **without** automatic proceed, low-priority process inspection, and references in both `launch-work` and `swarm` guidance. Never run an uncontrolled mixed-project stress test under this issue.

After implementation, migrate Bento's `launch-work` and `swarm` guidance and any other `run-heavy` call sites to the installed v1 entrypoint with explicit labels/weights. A compatibility `run-heavy` shim may exist during migration, but it must call v1 and never retain `HEAVY_MAX_WAIT`'s proceed-anyway behavior; update the test that currently asserts that behavior. Mark `docs/specs/2026-06-18-run-heavy-load-regulation-design.md` superseded only when the new entrypoint and call sites actually land. Every downstream adapter issue should cite this document and use the CLI/result/event contract above before becoming ready. Adapter work and a mixed-project stress run are separate tasks.
